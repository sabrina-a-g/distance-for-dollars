The D4D System Map

Not just the Strava piece — the whole thing. How a request travels from a browser to the database and back, how code actually ships, and how we’ll find out something broke before a user does.

Three ways to read this

Follow the request: browser → DNS → Ingress → the app → Postgres, with a side trip out to Strava whenever the app needs to read or refresh activity data. That side trip is its own nine-step handshake, mapped separately in the Strava Handshake reference — this map only draws it as one arrow.

Follow the code: a push to GitHub triggers Actions, which builds the image, pushes it to ECR, and Helm rolls it out to the k3s cluster already running on the EC2 box. None of that exists yet; right now shipping means building and running the Docker image by hand.

Follow the alarm: Prometheus and Grafana watch the cluster itself, Sentry catches errors from inside the app, and UptimeRobot pings the public URL from the outside. The Sentry arrow is labeled with D4D-30 on purpose — alerting on a failed Strava sync matters more than generic errors, because we already know token refresh is the part most likely to quietly break.

Reflects Jira status as of today — a living map, not a spec. Companion reference: The Strava Handshake (zooms into the single arrow between D4D App and Strava above).
